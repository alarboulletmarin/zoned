# Agent API, v1

How an AI agent (ChatGPT, Claude, any LLM with a browsing or fetch tool) reads the Zoned catalogue, builds a training plan from it, and hands the plan back to the user inside Zoned. Kept in English because it names code, like [workout-format.md](workout-format.md).

- **Everything is static.** No serverless function, no account, no key. The API is a set of JSON files written at build time; the plan comes back through a link whose payload sits in the URL fragment, which the browser never sends to a server.
- **Source of truth:** [`src/lib/agentApi/`](../src/lib/agentApi/). The build script [`scripts/generate-agent-api.ts`](../scripts/generate-agent-api.ts) only writes what that module returns, and the `/plan/import` page validates with the same module. If this document and the code disagree, the code is right and this document is a bug.
- **Entry point for agents:** [zoned.run/llms.txt](https://zoned.run/llms.txt), generated by the same script, with live, valid example links.

## Resources

All under `https://zoned.run/api/v1/`, served with `Access-Control-Allow-Origin: *`, `Content-Type: application/json; charset=utf-8`, and `Cache-Control: public, max-age=300, s-maxage=3600, stale-while-revalidate=86400` (`vercel.json`).

| Path | Content |
|---|---|
| `index.json` | `apiVersion`, `generatedAt`, licences, links to every resource, counts, the prebuilt plan list, the import link format. |
| `zones.json` | The 6 zones: `vmaPercent` and `hrMaxPercent` bounds read from `lib/zones.ts`, names, sensation and usage from `ZONE_META`. |
| `workouts.json` | Light index: `id`, `name`, `nameEn`, `discipline`, `family`, `category`, `sessionType`, `difficulty`, `typicalDuration`, `zones`, `phases`, `environment`, `url` (the page), `json` (the detail). Plus `count`, `byDiscipline`, `byFamily`. |
| `workouts/{id}.json` | One workout in full. Every index field, then description, coaching tips, common mistakes, variations, and the session itself (below). |
| `plans/prebuilt/{slug}.json` | A prebuilt plan, resolved: phases, then weeks with `day`, `workoutId`, workout names, session type, key flag, duration, notes, and the workout's `json` link. |
| `schema/plan-import.schema.json` | JSON Schema (draft 2020-12) of the import payload. |

`llms.txt` and `llms-full.txt` (every workout as compact Markdown, grouped by family) sit at the site root.

### Fields worth knowing

- `discipline` is `running | cycling | swimming | strength`: the agent's first filter. Running is the core of the catalogue; cycling and swimming are secondary.
- `family` is the shelf: the running `category` (`endurance`, `vma_intervals`, `long_run`, `trail`...), or `strength`, `cycling`, `swimming`.
- `phases` are the training phases the plan generator would schedule a workout in. An empty array means manual selection only (`REC-003`, a post-race flush run).
- `environment` is `null` for strength. Respect `requiresHills` and `requiresTrack`: they gate whether Zoned itself would schedule the session.
- `zones` are the zones a workout touches, as `Z1`...`Z6`.

### The session in a workout detail

A running-shape template (running, cycling, swimming) is published twice, on purpose:

- `structure.{warmup,main,cooldown}` is the **canonical, machine-readable** form: the `WorkoutStep` tree (`segment` and nested `repeat`) described in [workout-format.md](workout-format.md#workoutstep-the-machine-readable-tree). It is present for every phase. `structureSource.{phase}` says whether it was `authored` (the template carries a `*Structure`) or `derived` from the display blocks, through `getWorkoutPhaseSteps`, the function the timeline, the exports and the share codec already use.
- `blocks.{warmup,main,cooldown}` is the **display copy**, the `*Template` arrays verbatim: what the athlete reads on the session page, prose first.

Why both rather than structure alone: `workout-format.md` does not call the `*Template` fields legacy. They are required on every template and are the human copy, while `*Structure` is optional in the type. In the data, every main set is authored as a tree today (250 of 250 running-shape templates), and 239 warm-ups and 245 cool-downs are; the remaining phases are empty in both forms. So an agent reasoning about durations and zones reads `structure`; an agent quoting the session to a person reads `blocks`.

A strength template has no step tree: `blocks` holds `StrengthBlock`s that reference exercises by id, with `sets`, `reps`, rest and intensity, plus `equipment` and `primaryMuscleGroups`. `llms-full.txt` resolves the exercise names.

`estimatedDurationMin` is derived from the tree (`getStructuredWorkoutDurationMinutes`) for running shapes and is the middle of `typicalDuration` for strength.

## Stability

Within **v1, fields are only ever added**. A field is never renamed, retyped or removed, and its meaning does not change. Consumers must ignore fields they do not know. A breaking change ships as `/api/v2/` next to v1, never in place.

Catalogue content changes without a version bump: workouts are added, copy is edited. An id, once published, keeps naming the same session (`docs/workout-format.md`, ids are permanent).

## The import link

```
https://zoned.run/plan/import#d=<payload>
https://zoned.run/plan/import?lang=en#d=<payload>     English interface
```

`/plan/import` is a public, `noindex` route. It decodes the payload, validates it against the catalogue, shows a preview (the plan's shape, then one row per week with its sessions), and saves nothing until the person presses **Add to my plans**, which calls `savePlan`.

### Encoding

`d` takes one of two encodings, told apart by a prefix base64url cannot contain:

| Form | Meaning |
|---|---|
| `#d=<base64url>` | The JSON payload, UTF-8, base64url without padding (`toBase64Url` from `lib/share/codec.ts`). |
| `#d=z1.<base64url>` | The same JSON, raw-deflated first (RFC 1951, no zlib header). `z1` is the encoding version. |
| `#j=<percent-encoded JSON>` | Lenient fallback for an agent that cannot run code. Prefer `d`. |

`planImportUrl()` in `lib/agentApi/importLink.ts` emits the plain form up to 2000 characters and deflates beyond. Measured on a 16-week plan with five sessions a week (`agentApi.test.ts`):

| Payload | Plain link | Deflated link |
|---|---|---|
| ids only | 4,396 characters | 586 |
| plus a note on three sessions a week | 8,532 characters | 844 |

Past ~8,000 characters some chat clients and QR codes truncate, hence `z1`.

```python
import base64, json, zlib
data = json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode()
plain = base64.urlsafe_b64encode(data).rstrip(b"=").decode()
deflated = "z1." + base64.urlsafe_b64encode(zlib.compress(data, 9)[2:-4]).rstrip(b"=").decode()
```

### Payload, `kind: "config"`

The inputs of an assisted plan; Zoned runs `generatePlan()` on them, exactly as `/plan/shared` does. Prefer this variant for a standard race plan: the generator owns periodisation, progression and paces.

```json
{
  "version": 1,
  "kind": "config",
  "raceDistance": "10K",
  "raceDate": "2027-05-30",
  "level": "intermediate",
  "daysPerWeek": 4,
  "longRunDay": 6
}
```

| Field | Required | Values |
|---|---|---|
| `raceDistance` | yes | `5K`, `10K`, `semi`, `marathon`, `trail_short`, `trail`, `ultra` |
| `raceDate` | yes | `YYYY-MM-DD`, today or later; 4 to 52 weeks after the start |
| `level` | yes | `beginner`, `intermediate`, `advanced`, `elite` |
| `daysPerWeek` | yes | integer 3-7 |
| `longRunDay` | yes | integer 0-6, 0 = Monday |
| `startDate` | | `YYYY-MM-DD`, defaults to today |
| `raceName` | | up to 120 characters |
| `goal` | | `finish`, `time`, `compete` |
| `vma` | | km/h, 8-30 |
| `targetPaceMinKm` | | min/km, 2.5-12 |
| `elevationGain` | | metres, 0-20000 |
| `currentWeeklyKm`, `currentLongRunKm` | | km |
| `includeStrength` | | boolean |
| `strengthPerWeek` | | integer 1-3 |

### Payload, `kind: "plan"`

A plan the agent wrote week by week.

```json
{
  "version": 1,
  "kind": "plan",
  "name": "Reprise 2 semaines",
  "startDate": "2026-11-30",
  "weeks": [
    { "phase": "base", "sessions": [
      { "day": 1, "workoutId": "END-001" },
      { "day": 3, "workoutId": "VMA-001", "note": "Rester facile sur les récupérations." },
      { "day": 6, "workoutId": "LR-013" }
    ] },
    { "phase": "base", "isRecoveryWeek": true, "sessions": [
      { "day": 1, "workoutId": "END-001" },
      { "day": 6, "workoutId": "LR-013", "durationMin": 60 }
    ] }
  ]
}
```

| Field | Required | Values |
|---|---|---|
| `name` | yes | 1-120 characters |
| `startDate` | yes | `YYYY-MM-DD`; another day than Monday is moved back to its Monday, with a warning |
| `weeks` | yes | 1-104 weeks |
| `weeks[].sessions` | yes | array, empty for a rest week; at most 2 sessions on the same day |
| `weeks[].phase` | | `base`, `build`, `peak`, `taper`, `recovery`; omitted, the split a free plan of that length gets (`calculateFreePhases`) |
| `weeks[].isRecoveryWeek` | | boolean; a recovery week is counted at 60 % volume |
| `weeks[].label` | | up to 60 characters |
| `sessions[].day` | yes | integer 0-6, 0 = Monday |
| `sessions[].workoutId` | yes | an id from `workouts.json`, or `__race_day__` to mark the race |
| `sessions[].note` | | up to 500 characters, shown on the session |
| `sessions[].durationMin` | | 5-600, fixes the duration instead of the workout's typical one |
| `raceDistance`, `raceDate`, `raceName`, `level`, `vma` | | as in `config` |

Each session is built by `sessionFromWorkout`, the path a session picked by hand in the plan editor takes, so an imported session carries the same session type, key flag, duration and precision as one added in the app. The plan is stored as a free plan (`planMode: "free"`) through `preparePlanForStorage`.

### Validation and errors

`validateImportPayload(raw, lookup, { today })` is strict and exhaustive: it reports every issue, not the first one, because its reader is the agent that has to fix the payload.

- Unknown fields are errors, at every level, so `workout_id` is caught instead of silently dropped.
- Each issue carries a `code`, a JSON `path` (`weeks[2].sessions[1].workoutId`) and `params`; `describeIssue(issue, "fr" | "en")` turns it into a sentence that names the place in plain words: `week 3, session 2: unknown workout END-999. Valid ids are listed in https://zoned.run/api/v1/workouts.json.`
- A near miss gets a suggestion: `end-1` answers `Did you mean END-001?`.
- `CUSTOM-*` ids are refused: they live in one browser's storage.
- Non-fatal adjustments are warnings, shown on the preview: a `startDate` moved to its Monday, an empty week.

On a rejected payload the page lists every issue and offers **Copy for my assistant**, which copies `formatIssueReport()`: one English line per issue, ready to paste back to the agent.

Codes: `not_object`, `unsupported_version`, `unknown_kind`, `unknown_field`, `missing_field`, `invalid_type`, `invalid_enum`, `invalid_date`, `date_in_past`, `out_of_range`, `race_before_start`, `weeks_out_of_range`, `text_too_long`, `unknown_workout`, `custom_workout`, `too_many_sessions_day`, `empty_plan`; warnings `start_moved_to_monday`, `empty_week`. New codes may be added within v1.

## For a future MCP server

`src/lib/agentApi/` is pure: no React, no i18next, no storage, no `import.meta.glob`. An MCP server is meant to be a thin layer over it: `loadAgentCatalogue()` and the `build*` functions for read tools, `validateImportPayload()` plus `planImportUrl()` for a "make the import link" tool, `describeIssue()` for its error text. Keep it that way: a module under `agentApi/` that imports a component or the i18n entry breaks the build script first.
